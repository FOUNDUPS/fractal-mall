# Evidence review

Write down the exact claim, question and pass condition before investigating. Seek the strongest available counterexample. Use a source permalink and revision, or an archival document with date, location and access scope. Record which materials the reviewing session actually inspected.

| A claim about… | Evidence to collect |
| --- | --- |
| Historical intent | Original manifest, diagram or dated revision and exact passage. Preserve conflicting versions. |
| Current implementation | Pinned source, symbol, caller, guard or fallback; state what that path can do. |
| Local execution | Invocation, revision, fixture, environment and observed result. |
| Integration or deployment | Correlated events through the claimed boundary or an identified deployed version with a reproducible observation. |
| Open-source adoption | Dependency declaration or import plus the actual use; record upstream version and license. A proposed alternative stays a candidate. |
| Improvement | Blinded grading, fixed evidence and compute budget, preserved failures and an unseen case. Report uncertainty. |

Label unsupported interpretations as inference, proposal or unknown. In Google Docs, reply on the passage's existing thread where possible. Keep the original claim and the disposition (adopted, adapted, deferred or rejected). Verify the edited text by reading it back. A second reviewer records whether the postcondition passed.

Use the pinned [WSP_15 scoring definition](https://github.com/FOUNDUPS/Foundups-Agent/blob/7432d31e5a68544d2bbab6715f02f64b0b5b6f85/WSP_framework/src/WSP_15_Module_Prioritization_Scoring_System.md) for queue priorities. Record each axis, sum, band and revision. Resolve differences with the current authoritative rule when a new revision is used. Use the applicable WSP_97 for execution and readback. Evidence labels describe the scope of the observation.
